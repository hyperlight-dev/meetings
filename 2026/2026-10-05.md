## cVM and cuVM with Hyperlight (Jarno)

Jarno: My thesis is on mutual zero-trust compute with Hyperlight. I'm working on spawning confidential VMs and micro-VMs, and I wanted to ask how realistic and feasible this would be.

Magnus: I have a bit of background on this; I work on confidential containers. You'll need remote attestation in Hyperlight. The challenge is how far you can get without Linux. AMD has upstream Linux support with drivers that let you get attestation reports from the PSP. You'd need to do this in firmware instead. The whole stack is very much tailored to running a full OS, and it's intentionally slow — that creates tension.

Magnus: For a 100 ms workload, you might need to wait 1 s to get the attestation. How micro do you want this to be for it to still make sense?

Jarno: Making it very micro isn't that important. KVM has ioctls for AMD confidential compute.

Dan: Hyperlight-Unikraft runs Unikraft inside Hyperlight. There's quite a bit of prior art on doing confidential compute with unikernels. It could be feasible to run confidential computing workloads with unikernels and with Hyperlight-Unikraft: <https://zenodo.org/records/17493275>.

Ludvig: Filing a HIP would be a good first step here.

Magnus: You might need to be a bit creative; it's not just about the docs on patching and attestation reports. Azure uses VMPL to carve out a part of the VM that contains a vTPM. It's not accessible to the guest, but it's also not fully accessible to the host, so you get a fast scratch space. Confidential computing needs a cryptographic proof to guarantee that you're running in a secure context. For a master's thesis, things don't need to be watertight. Coconut is a good reference project.

Jarno: Someone mentioned firmware attestation primitives?

Magnus: If you don't have a kernel driver, you have to interface with the security chip through very low-level means. That might be challenging.

Jarno: I like a challenge.
