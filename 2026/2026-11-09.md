### HIP 0008: Postcard serialization for host-guest messages ([hyperlight-dev/hyperlight#1999](https://github.com/hyperlight-dev/hyperlight/pull/1999))

James: who owns the length of guest memory? Does the host own that length?

Ludvig: the guest might own that length? guest -> host can own it

James: do we cap that? if the guest makes it big it could cause overflows / spill over

Tomasz: no different than what we have now with FlatBuffers where we prefix the buffers with the size. It needs to be checked against the capacity of the queue. Anything that is coming from the guest needs to be checked against the settings, e.g. queue capacity. There is a bunch of verification that we need to do.

Ludvig: not too different from what we do with FlatBuffers

Simon: the old stack-based system could not overflow beyond that memory because it had to fit in that space.

Simon: motivation mentioned perf, no more generated code, and finally a point about security. We can measure the first two, the third one I don't know how to measure. Can we think of a way to evaluate that?

Ludvig: it's not like we're serializing objects in e.g. Java. There's not much we need to check?

Simon: was more the statement that we are now equally secure if not more secure.

Ludvig: good feedback!

Jorge: the serialization attack surface we care about is object confusion; using concrete types with Serde, that cannot happen. That stays the same in both cases. If we keep the list of possible fn params as a finite enum it stays the same. If we open that up to user-defined data that might cause problems. But that would be outside of the user-provided boundary of HL.

Simon: how do we at least write down that that assertion is true if we cannot prove it. I'm not disputing the claim.

Ludvig: I'll think about it.

Jorge: Maybe we can say it satisfied the internal usage constraints for us?

Ludvig: maybe?

Simon: compare and contrast with FlatBuffers and see if there's a gap?

Ludvig: I'll work on it.

### hyperlight — `impl Drop` for host resources in the guest ([hyperlight-dev/hyperlight#810](https://github.com/hyperlight-dev/hyperlight/issues/810))

Jorge: we wanted components to be the way to discuss the interface between guest/host

James: when you're using resources in hl-wasm, if you let go of them from the guest they don't get released on the host so you leak memory.

Simon: WIT being the canonical way to describe the guest/host in HL - the objection I've had with this is the issue this raises: folks using HL, they have a bunch of APIs defined by C header files they don't want to use a bunch of C API functions. It feels weird at the moment that it's in HL.

Simon: we should either finish the job or remove it. It's not actually being used anywhere; either finish it or remove it.

James: it's used in HL-wasm, but not elsewhere.

Yosh: feels like a 1.0 question?

Jorge: yes - when you create a sandbox, by default we could use Postcard for Serde. We have two levels of serialization: the control plane used for functioning of the sandbox, and another layer, where we serialize the function arguments etc. with a fixed enum. We want to go from FlatBuffers to Postcard and Serde. For the control plane we want to fully control the serialization. For the data plane, we should leave that configurable. For HL-wasm it could specify a different argument, e.g. WIT + canonical ABI. I am partial to that plan.

Tomasz: we are already agnostic by providing the bytes type in our protocol? If you need JSON you can just tunnel that through bytes.

Jorge: we are paying the cost twice with FlatBuffers.

James (in chat): this needs a HIP

Yosh: let's follow up offline
