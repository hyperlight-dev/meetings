### HIP 001: Ring Buffers for Hyperlight ([#1112](https://github.com/hyperlight-dev/hyperlight/pull/1112))

Tomasz: the proposal is one thing. the impl is another and has been ongoing for some time already. building blocks have been merged, floating/unconnected. 2-3 weeks ago replaces the stack-based comms in hyperlight with virtio communication. want to talk about this PR. the PR is probably too big as it is now to get a meaningful review.

PR: https://github.com/hyperlight-dev/hyperlight/pull/1717

Tomasz: this pr is implementing this proposal:

https://hackmd.io/D2nhunuGSXWhH7aWmS9jXA?view

Tomasz: this is an optimization for serialization of large chunks of memory. we're copying this data for large chunks of memory

Sienna: if we're talking about buffer serialization I'd like to focus on zero-copy semantics as much as possible for perf reasons.

Tomasz: this proposal is exactly that. There are some tractions between zero-copy and safety. We cannot expose memory to host, have to copy it out. This PR is including this optimization and replacing stack-based comms with virtio. That should potentially create two PRs of equal size. If anyone else sees any other blockers with this PR, let me know. 

Tomasz: discussed ownership of virtio buffers: host-owned to guest-owned. Currently the PR is preserving the semantics of input/output regions. Change the ownership model. I suggest we don't do that in the first PR, but do that as a follow-up.

Sienna: question about polling; specifies polling a single memory location which I'm happy about. Are you imagining a polling-based integration? Tokio uses mio to poll readiness. Or is polling based on the speed at which the host can read from memory (note: hope I got this right)

Tomasz: initially just replace the communication we have now. Polling will be initially internal to crates use. Long run we want to expose an async interface for host. Basically the virtual queue is supposed to be a primitive for async calls and streams. We don't yet have a proposal for that though. We're also using virtual queue so we have a pretty good concurrency model so we can run host and guest concurrently. Should provide us with a building block for Wasm p3 features.

Tomasz: does that sound good to you? I believe Ludvig was looking at the PRs?

Ludvig: I think a big thing was a lot of code review at the time.

Tomasz: Will look at splitting; required stubbing.

Ludvig: as long as we land it before the release

Magnus: stacked PRs could be helpful for this; it's good for large-scoped PRs

Tomasz: having CI pass for each atomic change.

Magnus: annoying at first to switch, but you profit from it at the end because you can cherry-pick and move things around better. think there are a lot of upsides.

Yosh: it sounds like the plan is:
1. Split the PR: optimization using bytes
2. Replacing stack based communication w/ virtio
3. Look to change ownership of buffers from host-owned to guest-owned (needs HIP)

Yosh: who would be good people to review this?

Tomasz: first part would be Ludvig and Jorge I think. Virtio-based communication are in shared memory are probably Lucy and anyone else.
