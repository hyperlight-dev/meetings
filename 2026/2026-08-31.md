Magnus: Do you require full Linux guest support for those use cases?

Dan: For your workloads you're just using core, not JS/Wasm/Unikraft?

Sienna: No, just core. We needed safe sandboxing for GPU compute. Cloud Hypervisor is great, but it's designed for full virtualization and requires e.g. virtio and other proprietary drivers. That requires a lot of net-new industry tech, which made it unviable from the beginning. Hyperlight core does one thing really well: sandbox lifecycles. Because of that we're building higher-order orchestration on top of it. We're building everything we need to run FaaS with actually cheap GPU compute. If you try to run multi-tenancy with a GPU it's either a huge security flaw or it requires full device allotments. We've proven in a lab that we don't need that; we can run without those limitations.

### HIP 001: Ring Buffers for Hyperlight ([#1112](https://github.com/hyperlight-dev/hyperlight/pull/1112))

Tomasz: The proposal is one thing; the implementation is another, and it has been ongoing for some time already. Building blocks have been merged, but they're floating/unconnected. Two to three weeks ago I put up a PR that replaces the stack-based comms in Hyperlight with virtio communication. I want to talk about that PR: it's probably too big as it is now to get a meaningful review.

PR: [hyperlight#1717](https://github.com/hyperlight-dev/hyperlight/pull/1717)

Tomasz: That PR implements this proposal: https://hackmd.io/D2nhunuGSXWhH7aWmS9jXA?view

Tomasz: This is an optimization for serialization of large chunks of memory. Today we're copying that data.

Sienna: If we're talking about buffer serialization, I'd like to focus on zero-copy semantics as much as possible for perf reasons.

Tomasz: This proposal is exactly that. There is some tension between zero-copy and safety: we cannot expose memory to the host, so we have to copy it out. This PR includes that optimization and replaces stack-based comms with virtio. Splitting it should produce two PRs of roughly equal size. If anyone sees any other blockers with this PR, let me know.

Tomasz: We discussed changing the ownership of virtio buffers from host-owned to guest-owned. Currently the PR preserves the semantics of the input/output regions. I suggest we don't change the ownership model in the first PR, but do it as a follow-up.

Sienna: Question about polling: the proposal specifies polling a single memory location, which I'm happy about. Are you imagining a polling-based integration? Tokio uses mio to poll readiness. Or is polling based on the speed at which the host can read from memory? (Note: hope I got this right.)

Tomasz: Initially we just replace the communication we have now. Polling will initially be internal to the crate's use. Long term we want to expose an async interface for the host. Basically the virtqueue is supposed to be a primitive for async calls and streams, though we don't yet have a proposal for that. We're also using the virtqueue so we have a good concurrency model and can run host and guest concurrently. It should provide us with a building block for Wasm p3 features.

Tomasz: Does that sound good to you? I believe Ludvig was looking at the PRs?

Ludvig: I think a big thing was that there was a lot of code to review at the time.

Tomasz: Will look at splitting it; that requires some stubbing.

Ludvig: Fine by me, as long as we land it before the release.

Magnus: Stacked PRs could be helpful here; they're good for large-scoped changes.

Tomasz: That would let CI pass for each atomic change.

Magnus: It's annoying at first to switch, but you profit from it in the end because you can cherry-pick and move things around more easily. I think there are a lot of upsides.

Yosh: It sounds like the plan is:

1. Split the PR: optimization using bytes [...]
2. Replace stack-based communication with virtio
3. Look at changing ownership of buffers from host-owned to guest-owned (needs a HIP)

Yosh: Who would be good people to review this?

Tomasz: The first part would be Ludvig and Jorge, I think. The virtio-based communication in shared memory is probably Lucy and anyone else.

Dan: Want to use this for Hyperlight Unikraft; can provide additional review by trying it out.

Sienna: Wonderful meeting the team! Sorry I joined late — the invite never arrived, otherwise I would have joined sooner. I've enjoyed working with Microsoft.
